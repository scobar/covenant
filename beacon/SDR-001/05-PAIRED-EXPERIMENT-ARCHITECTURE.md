# SDR-001 — Paired Experiment Architecture

> **SDR-001 v0.1 — NONCANONICAL SUCCESSOR-DESIGN RESEARCH — NO SIG-002 ATTEMPT, STREAM, HOLDOUT, OR MODEL TRIAL**

This architecture governs a possible future comparison. It does not assemble
a packet, instantiate a condition, select a provider, or authorize execution.

## Shared source and condition freeze

1. Create one frozen abstract semantic source under a later accepted decision.
2. Generate one surface-novel baseline condition and one surface-novel
   treatment condition from that source.
3. Prove identical semantic content, identical nonframing event bytes,
   identical framing-cue multisets, and identical total framing-event counts.
4. Freeze both conditions before decoder or provider selection where feasible.
5. Record and disclose any stream-length, cue-budget, or parse-complexity
   mismatch; a cue-budget or semantic mismatch stops a locality-only claim.

## Opaque conditions and order

- Randomize condition identities to opaque `Condition A` and `Condition B`.
- Retain the filled mapping off-repository until applicable outputs and scores
  freeze.
- Randomize or counterbalance order where feasible and preserve the method.
- The same provider, displayed model configuration, neutral instruction,
  settings, and tools must apply to both conditions. A change makes the pair
  not comparable unless a later protocol explicitly treats it as a different
  replication question.

## Context isolation and provenance

- Use one fresh, isolated context per condition.
- No context may see the other condition, the other output, a target outcome,
  a solution, or a comparison.
- Preserve complete prompts, settings, tools, UI labels, hidden-setting
  limitations, timestamps, order, and operator provenance.
- Preserve prior-exposure, same-provider, repository, retrieval, and hidden
  backend limitations for each condition.

## Run and retry rules

- Request one substantive output per condition.
- Freeze every run attempt and candidate-specific output.
- Permit no substantive retry.
- Permit a technical retry only under predeclared invalidity rules and with
  the identical condition and configuration.
- A failed, partial, indeterminate, critical, or unfavorable output is not a
  technical invalidity.
- Do not perform best-of-N, favorable-output selection, selective retention,
  or post-result prompting.

## Output, scoring, and comparison chronology

1. Freeze the raw output and execution metadata for each condition.
2. Classify technical validity and contamination under the frozen rules.
3. Score each condition independently against the candidate-specific frozen
   Levels 0–4 scorecard.
4. Freeze each complete score and dissent record.
5. After both candidate-specific scores freeze, unblind or verify the opaque
   mapping under the applicable frozen chronology.
6. Compare the frozen candidate-specific results using only the vocabulary in
   `06-SCORECARD-CONTINUITY-AND-GUARDRAILS.md`.

The mapping, commitment verification, or comparison cannot retroactively
change a raw output, validity class, score, or dissent. There is no aggregate
score, candidate-wide winner, or favorable-output selection.

## Denominators and reporting

- Exclude technically invalid and protocol-invalid runs from valid
  denominators while preserving them.
- Keep exposure classes stratified.
- Disclose same-provider dependence and unknown backend identity.
- Treat a paired result as conditional on the exact design, provider/model
  configuration, context, tools, prompt, order, and trial method.

## Dormant zero-cost option

Authorized incremental spend is USD `0`. If a zero-cost or adequately isolated
paired execution is unavailable, the architecture may remain dormant
indefinitely. No provider, model, holdout, packet, trial, or execution is
selected here.
