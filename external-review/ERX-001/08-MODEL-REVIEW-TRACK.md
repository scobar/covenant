## Procedural label blinding

Before response freezing, a reviewer-facing model packet may contain only
opaque Review, Assignment, and Packet IDs; neutral candidate labels and alias
filenames; neutral scenario labels and alias filenames; a packet version; and
an opaque packet-instance commitment. It must not contain canonical candidate
or scenario identities, paths, hashes, Git blobs, or the raw hash of an exact
candidate alias. The administrator separately verifies canonical source bytes
and keeps the mapping outside reviewer-facing materials until all applicable
candidate-specific and comparative responses freeze.

The packet-instance commitment is not a candidate hash and cannot by itself
identify the candidate. It may later help detect post-hoc remapping, but it
does not prove fair randomization, source claims, reviewer ignorance, or moral
authority. It is not a blockchain. The repository is public, and supplied text
may still be recognized or found; procedural label blinding cannot guarantee
ignorance. No mapping, nonce, commitment, packet, assignment, prompt
submission, or response is created in this preparation task.

## Fresh-context requirements

For a paired model review:

1. Start a fresh context for Candidate A.
2. Freeze the Candidate A output.
3. Start a fresh context for Candidate B.
4. Freeze the Candidate B output.
5. Start a third fresh context for comparison only after both candidate-specific outputs are frozen.

The comparison context may receive the two assigned candidates and their frozen candidate-specific outputs under the predeclared packet and prompt procedure. No candidate-specific context receives:

- The other candidate
- The other candidate-specific output
- Prior project outcomes
- Candidate lineage
- Candidate version labels
- A target result

A single-candidate model review uses one fresh candidate-specific context and does not receive comparative materials.

## Prompt preservation

The operator must preserve:

- Full system prompt
- Full developer prompt
- Full user prompt
- Tool configuration
- Web-access status
- Files supplied
- Files withheld
- Model settings
- Model-reported identity
- Provider
- Interface
- Timestamp
- All valid outputs
- Retry and selection method

The record should also identify context limits, truncation, memory, prior context, operator interventions, and any unavailable setting. Model self-identification is operator-reported metadata, not independent verification.

## Tool and web access

Unrelated tools and web access should be disabled when the review interface permits it. If any tool or web access is available:

- Disclose the capability.
- Record whether and how it was used.
- Preserve retrieved sources and tool outputs.
- Before the applicable responses freeze, do not hash candidate or scenario
  text and compare it with public values, search exact phrases, search
  canonical-looking scenario identifiers, or browse the repository to infer a
  mapping.
- If exposure occurs, record what was done, when it occurred, what was learned
  or inferred, and which response sections were completed before exposure.
- Do not call the result procedurally label-blinded if the model searched the public repository or the supplied candidate text outside the packet.

The repository is public, and **procedural label blinding** cannot guarantee that a model or operator lacks prior exposure. Exposure does not automatically invalidate an output, but it changes its method classification and must be disclosed.

## Model-family diversity

- Multiple outputs from the same model, provider, shared system, or coordinated context are repetitions, not automatically independent evaluator diversity.
- Different provider or model-family labels do not prove independent training, assumptions, or reasoning.
- Operator selection and prompt design remain shared influences.
- Correlated tools, retrieval sources, safety layers, and evaluation prompts may introduce additional shared influences.
- Model review does not represent future superintelligence.
- Model output is not assent.

## No selective retention

A future operator must predeclare:

- Requested run count
- Retry conditions
- Failure-handling rules
- Selection method
- Whether all valid outputs will be retained

All valid outputs must be retained. Invalid or failed runs, their criteria, and their disposition must be disclosed. A run must not be repeated solely to seek a favorable outcome, and an unexpected conclusion must not be discarded merely because it is unexpected.

## Security and privacy

Do not include private reviewer, operator, participant, or project-contact data in model prompts. Use pseudonymous review identifiers where needed. Minimize personal data in files, retrieved sources, logs, and preserved outputs, and review all material for unintended disclosure before any later publication.
